# Bundled reference data

## `usda-foods.json`

The USDA [FoodData Central](https://fdc.nal.usda.gov/) generic reference foods (public domain, CC0): the **Foundation Foods + SR Legacy** datasets, each pruned to its per-100g nutrient profile (energy, macros, fat breakdown, and the FDA-label vitamins & minerals), its USDA food `category`, and named `portions` (e.g. "1 large" egg → 50 g) for count-unit ingredients. Each record keeps its `fdcId` for provenance. The Branded set (~400k branded products, ~3 GB) is intentionally excluded — it is not useful for ingredient matching — and the commercial branded products that SR Legacy mixes into the generic data (candy bars, named smoothies, restaurant dishes, infant formula) are filtered out by `scripts/usda-brands.mjs`, so an "apple" query never lands on "Candies, NESTLE …". The same filter keeps the dataset to base cooking ingredients: it drops enriched (fortified) grain forms in favour of the unenriched base ("unenriched" entries are kept), and removes processed/finished forms by rule — sweetened, fortified, flavoured, instant, microwaved, UV-light-treated, overripe and restaurant-prepared variants, carbonated drinks, fruit nectars, imitation products, breaded/par-fried items and drink mixes (the plain base food stays; "unsweetened"/"not fortified"/"unflavored" are kept) — plus finished-dessert groups (cakes, cookies, pancakes, toaster pastries) and a curated by-id denylist. Finished/processed foods with no clean reusable pattern (specific alcoholic drinks, ice creams, prepared composite dishes, candied/cured items) are listed by id with their description + sweep group in `scripts/usda-curation-drop.json` (provenance, like `scripts/usda-exclude.json`). Newer USDA **Foundation** re-analyses re-use the SR Legacy name of the same food, so exact-duplicate descriptions are collapsed to the single most-complete record, and an incomplete analysis that carries no energy and no full macro panel is dropped (its complete sibling is kept), so a match never silently contributes 0 kcal. Beyond USDA, the bundled file also carries the curated **custom foods** (`custom-foods.json`, composite ingredients USDA has no generic entry for) and the curated **national-table foods** (the `enCurated` subsets of `japan-foods.json` and `france-foods.json`), merged in by `fdcId` so the authoring picker draws on one combined dataset.

The file is several MB, so the authoring island fetches it **lazily** via its asset URL (a `?url` import in `addLib.ts`) rather than bundling it; it is never shipped to the public recipe pages.

A full re-ingest from source is rare (needs `curl` and `unzip`; no API key required); its script is archived under `scripts/old/`:

```sh
node scripts/old/build-usda.mjs
```

The script downloads both bulk datasets and prunes them to the fields above. Energy comes from USDA's reported value (nutrient 208) when present, else the Atwater **specific** factor (958), else the **general** factor (957), else the standard 4·protein + 9·fat + 4·carb + 7·alcohol calculation from the food's own macros — so newer Foundation foods that ship no pre-computed energy row still carry one. It then dedupes by `fdcId`, collapses exact-duplicate descriptions to the most-complete record, drops energy-less analytical references and the branded/curated/enriched forms (`scripts/usda-brands.mjs`), and overwrites this file — so a re-ingest reproduces the cleaned dataset rather than reintroducing them. See the script header for the dataset URLs and the nutrient-number → field mapping.

To re-apply the brand filter to the committed file without re-downloading (e.g. after editing the filter, its denylist `usda-exclude.json`, or its keep-list, or to cut a food via `usda-curation-drop.json`), run `node scripts/old/prune-branded.mjs` (`--dry-run` to preview). Both entry points refuse to write if filtering would orphan a `food-scoring.json` entry.

### Nutrient gap fills

USDA leaves many fields blank (sugars, fatty-acid fractions, vitamins E and K, choline, polyols…), and a blank field is not a zero, so `scripts/fill-nutrient-gaps.mjs` fills a missing field only with a value of known quality, following the FAO/INFOODS compilation guidelines' preference for analytical data over estimates (Greenfield & Southgate 2003; FAO/INFOODS 2012). Nothing is imputed from a merely similar food: a field with no such value stays missing, so the engine can surface the gap honestly. A measured USDA value is never overwritten. Each filled field is recorded on the food as `gapFill: { field: "<METHOD>:<source>" }`, with one of four methods, tried in this order:

1. `ANALYSED:USDA-FDC:<fdcId>#<nutrient number>` — the food's own FoodData Central record reports the analyte under an alternate nutrient definition the compact shape does not read: total sugars as "Sugars, Total" (269.3) and dietary fibre by AOAC 2011.25 (293), both common in Foundation Foods, or vitamin D as its D2 + D3 components.
2. `CALCULATED:kcal×4.184` / `CALCULATED:kJ÷4.184` — exact unit conversion between the two energy fields, nothing else.
3. `ZERO:<rule>` — a nutrient that is biochemically absent, by these rules only:
   - `carb-free` — sugars, fibre and polyols when total carbohydrate is 0 (they are components of it).
   - `fat-free` — saturated, mono-, polyunsaturated and trans fatty acids, EPA and DHA when total fat is 0 (components of it).
   - `plant-food` — cholesterol in plant foods (an animal sterol; plants make phytosterols); vitamin B12 in plant foods except seaweeds/algae, ferments (tempeh, natto, miso, kimchi…), yeasts and fortified products (B12 is made only by microorganisms); vitamin D in plant foods except mushrooms, yeasts and fortified products (D2 forms from UV-exposed fungal ergosterol); the long-chain omega-3s EPA and DHA in plant foods except seaweeds and algae (they are made by marine microalgae; land plants lack the desaturases to form them). "Plant food" is a plant USDA category (fruits, vegetables, legumes, grains, nuts and seeds, spices, mushrooms), a plant oil, or a plain juice/tea/coffee, with no animal ingredient named.
   - `animal-food` — dietary fibre in plain fish, shellfish, eggs and unflavoured dairy (fibre is plant carbohydrate polymer by the Codex 2009 definition).
   - `no-caffeine-plant` — caffeine in foods that name no coffee, tea, cocoa/chocolate, cola, guarana, mate or kola (the only dietary caffeine sources).
   - `not-fermented` — alcohol in foods that are neither alcoholic drinks nor fermented (bread, yoghurt, cheese, vinegar, soy sauce, miso, kombucha, extracts… are excluded) and not beverages.
   - No zero rule exists for polyols or trans fat beyond the definitional ones: no authority states their absence for a whole food category (trans fat occurs naturally in ruminant fat and forms in oil refining and frying), so those stay missing unless a table reports them.
4. `BORROWED:<SOURCE>:<code>` — an analysed value for the same food in the same state (raw/cooked/dried/canned, same variety where it matters) from another official table: another FDC record with the identical description (the twin `dedupeByDescription` collapsed), or a hand-reviewed exact match in `scripts/nutrient-gap-crosswalk.json` to USDA SR Legacy / Foundation (`USDA-SR`, `USDA-FOUNDATION`, by fdcId), Ciqual 2020 (`FR-CIQUAL`, by alim_code), MEXT 2023 (`JP-MEXT`, by food number) or the Danish Food Composition Database 6.1, "Frida" (`DK-FRIDA`, by FoodID). A crosswalk entry may `exclude` fields that differ between the two records (e.g. the enrichment vitamins when the only same-food twin is the enriched form). Reviewed foods with no exact match in any table are kept in the crosswalk as `{ source: null, note }`, so the review is not repeated. `--suggest` prints same-state candidates for the remaining gaps of recipe-used foods to review by hand; `--gaps` prints those gaps. Review rules: same species (and variety where it changes composition, e.g. Florida vs Hass avocado, wild vs farmed trout), same state, and for dairy a fat content within about 10 % (fatty-acid fractions scale with milk fat); selenium is excluded when borrowing a plant food across countries, since it follows soil selenium rather than the food. Frida (`scripts/lib/frida.mjs`) records a source for every value, and only analytical values are borrowable: values from DTU analyses, journal articles and reports (EuroFIR reference types A, AJ, AB, R, P, PA, and named one-off analyses X) are kept; a value "calculated by converting various analytical data" (source 1003 — a sum such as total sugars, polyols or saturated fatty acids, or a vitamin total) is kept only when every component of that sum present for the food is itself analytical; estimates, recipe calculations, values copied from other countries' tables or handbooks (some are USDA itself) and label values are dropped. Frida's vitamin A column is retinol equivalents, so `vitA_ug` is recomputed as RAE (retinol + β-carotene / 12) from its analytical retinol and β-carotene; vitamin E is α-tocopherol and niacin is preformed niacin, matching USDA. Frida's choline values all come from other tables, so Frida fills no choline.

The fills live in `nutrient-gap-fills.json` (fdcId → field → `[value, provenance]`), and `serializeFoods` (`scripts/usda-brands.mjs`) layers them onto every food it writes, so both write paths (`build-usda.mjs`, `prune-branded.mjs`) keep them; a food's original values are its `n` minus the fields in its `gapFill`, so re-running is idempotent. Rebuild with `node scripts/fill-nutrient-gaps.mjs` (`--dry-run` to report only); it reads the git-ignored Ciqual XML (see `france-foods.json` below) and the Frida 6.1 workbook (`scripts/data-raw/frida/FCDB_6.1_Dataset.xlsx`, downloaded from https://doi.org/10.11583/DTU.32312844), and downloads the FDC Foundation + SR Legacy bulk JSON once into the git-ignored `scripts/data-raw/fdc/`. `src/data/usda-foods.test.ts` checks that every stored value is finite and non-negative, that every filled value carries an allowed provenance, and that none is imputed, and reports the fields still missing.

### `nova`

Each food carries a burnt-in NOVA processing group (1 minimally processed, 2 processed culinary ingredient, 3 processed, 4 ultra-processed), assigned by `scripts/nova.mjs` from its name and category and stamped by `serializeFoods`; `food-nova-overrides.json` corrects, by fdcId, the foods whose name carries no marker the rules can see (national-table ferments, formulated plant drinks, prepared sauces). The rules follow the NOVA definitions (Monteiro 2019): grinding, drying, roasting and non-alcoholic fermentation keep a food in group 1, so a plain or unsalted nut butter or tahini stays 1, a salted one is 3, and a sweetened, hydrogenated or reformulated one is 4; distilled spirits, mass-produced packaged bread, industrial pastry, pressurised cream toppings, flavoured yoghurts and non-sugar sweeteners are 4; table olives and oil-roasted nuts are 3. Generic reference foods hide the additives that would make a retail product ultra-processed, so the group is an estimate, as NOVA's low inter-rater agreement also implies.

## `japan-foods.json`

The Japanese national reference foods — MEXT [Standard Tables of Food Composition in Japan – 2020 – Eighth Revised Edition (Supplement 2023)](https://www.mext.go.jp/a_menu/syokuhinseibun/mext_00001.html), ~2,500 generic foods — pruned to the same per-100g nutrient shape as `usda-foods.json` and tagged `source: "JP-MEXT"`. fdcIds are namespaced into the `81_000_000` band (`81_000_000 + MEXT food number`) so they never collide with USDA or custom ids; each food keeps its MEXT `foodCode` and native `nameJa`. MEXT ships no English names, so `description` is a curated English name for the foods recipes use, otherwise a Hepburn romanisation of the kana (`scripts/lib/romaji.mjs`) — kanji-heavy names keep their native form, and English coverage grows as recipes need it. It is a generic reference table with no branded entries, so it needs no brand filter.

Foods that got a curated English name are flagged `enCurated: true`. That flag is the matchable subset: `serializeFoods` (in `scripts/usda-brands.mjs`) merges only the `enCurated` foods into the bundled `usda-foods.json`, so the authoring picker matches a regional ingredient (mirin, shimeji, katsuobushi…) against real national-composition data, while the romanised siblings — whose short romaji names would otherwise collide with English words and out-rank the clean USDA generic (e.g. `wakame`, `sake`) — stay out of matching. The matcher tie-breaks domestic-first (see `src/core/match.ts`), so a national food wins a regional term only by out-scoring the USDA proxy. The full table stays here for provenance and to grow the curated subset over time.

Regenerate it from three git-ignored MEXT Excel inputs in `scripts/data-raw/` (the main table plus the fatty-acids and carbohydrates supplements, joined on food number) with:

```sh
node scripts/build-japan.mjs
```

satFat/MUFA/PUFA come from the fatty-acids supplement and total sugars from the carbohydrates supplement (summed from the component mono/di-saccharides). MEXT's special values map as `Tr` → 0, `(x)` → estimated `x`, `-`/blank → unknown (field omitted).

## `france-foods.json`

A curated handful of French national reference foods from the ANSES [Ciqual 2020 French food composition table](https://ciqual.anses.fr/) (CC-BY 4.0 on Zenodo, Etalab Open Licence on data.gouv.fr — attribution required; XML release on [Zenodo](https://zenodo.org/records/4770600), DOI 10.5281/zenodo.4770202), pruned to the same per-100g nutrient shape as `usda-foods.json` and tagged `source: "FR-CIQUAL"`. It fills specific gaps the USDA generics leave — potato gnocchi, nutritional yeast, plant-based soy cooking cream (Ciqual 11214, the plant-based stand-in for cooking cream), plain unsweetened soy yogurt (Ciqual 19693, the plant-based stand-in for yogurt, sour cream and crème fraîche) — and adds a second, European reference for oat drink and whole-wheat pasta. Only the foods listed in `CURATED_EN` in `scripts/build-ciqual.mjs` are emitted: the full ~3,200-food table is not needed, because every Ciqual food the matcher uses is picked by hand and given a USDA-style English name. All of them are therefore `enCurated: true` and merged into `usda-foods.json` by `serializeFoods`, with the same domestic-first tie-break as the MEXT foods (a Ciqual food wins only by out-scoring the USDA candidate). fdcIds are namespaced into the `82_000_000` band (`82_000_000 + Ciqual alim_code`); each food keeps its Ciqual `foodCode` and native `nameFr`, and its `category` is the closest USDA category for its Ciqual sub-group.

Regenerate it from three git-ignored Ciqual XML inputs in `scripts/data-raw/` (`ciqual-2020-alim.xml`, `ciqual-2020-compo.xml`, `ciqual-2020-const.xml` — the `alim_`, `compo_` and `const_2020_07_07.xml` files of the release, renamed) with:

```sh
node scripts/build-ciqual.mjs
```

Energy is the Regulation (EU) 1169/2011 value (kcal and kJ); for a curated food Ciqual publishes without one (the soy cooking cream), `build-ciqual.mjs` derives it from the food's own analysed protein, available carbohydrate, fat, fibre, polyols, alcohol and organic acids with the same regulation's Annex XIV conversion factors, an unmeasured component counting as zero. Protein is Ciqual's N × Jones-factor value, and vitamin A is µg RAE = retinol + β-carotene / 12, emitted only when both are known. Ciqual's `Glucides` is *available* carbohydrate, so `carbs_g` stores it plus fibre — the USDA "by difference" total the engine expects (it subtracts fibre and polyols itself). Ciqual's special values map as `traces` → 0, `-` → unknown, `< x` (below the quantification limit) → unknown (field omitted).

## `food-scoring.json`

Cited scoring metadata keyed by `fdcId`, merged at author time by the glycemic engine (`src/core/gi.ts`) and the matcher. Foods without an entry still contribute nutrients (and macros/Nutri-Score/inflammation), just no GI. Kept separate from `usda-foods.json` so regenerating the USDA nutrients never wipes the values. Per food, optional:

- `gi` + `giSource` + `giConfidence` — the food's glycemic index, on the 100-point glucose scale, sourced from the Atkinson 2021 international tables (see `gi-reference.json` below). **Every** food carries a GI so no recipe can ship a blank dial; `scripts/match-gi.mjs` assigns each one through a documented ladder, recorded in `giConfidence`: **high** (an as-eaten staple reference — the mean of the Atkinson entries for the boiled/cooked food, e.g. white spaghetti, wholemeal spaghetti, rolled-oat porridge, brown rice, so a dry and a cooked record of one staple share its GI — or a strong same-category match to a specific reference food), **medium** (partial same-category match), **predicted** (no match — an available-carb-weighted blend of the food's sugar at GI 65 and its starch at the food's category-median GI, a composition estimate in the spirit of Rytz 2019), or **low** (a non-starchy / minor carb source under 10 g available carb/100 g gets a low nominal GI; a starchy food with no sugar figure gets its category-median GI). Foods under 0.5 g available carb/100 g (oils, water, salt) are recorded as GI 0 — carb-free by convention, and never reach the composite, which ignores contributions below 0.5 g. `giSource` names the exact reference food, proxy, or estimate basis. Existing values are preserved across re-runs — the matcher never overwrites a GI already present, so hand-curated values and prior matches survive untouched — except that `--rematch-predicted` clears and re-assigns the estimated tiers (`predicted`, `low`) after the reference table or matcher improves. Pasta and noodle foods in USDA's combined "Cereal Grains and Pasta" category are matched against the PASTA AND NOODLES reference category, and USDA's "Baked Products" category is split by name into the BREADS, CRACKERS and COOKIES reference categories (the rest — cakes and pastries — against BAKERY PRODUCTS; wonton wrappers, a boiled wheat dough, against PASTA AND NOODLES). Common breads are as-eaten staples too: each bread type (white wheat, wholemeal wheat, rye, pumpernickel, white and wholemeal pita, naan, chapati, whole-wheat roti, corn tortilla, rusk/melba toast) takes the mean of its plain, unmodified Atkinson entries, a toasted record shares its bread's GI, and dried breadcrumbs, croutons, US "wheat bread" and saltines take the white-bread or plain-cracker mean at **medium** confidence. Matching normalises plurals ("Mangos" ↔ "Mango") and, among near-equal candidates, prefers a cooked/boiled reference entry.
- `fvl` — whether the food counts toward Nutri-Score's fruit/vegetables/legumes share. Curated `fvl` takes precedence; otherwise it is approximated from the USDA category (fruits/vegetables/legumes, excluding starchy tubers, nuts, oils, juices and obviously-processed forms). This category heuristic is coarse — like all scores it is an estimate, confirmed per-ingredient in the review step.

A build-time guard (`src/core/recipeScore.repro.test.ts`) fails if any recipe has meaningful available carbohydrate but no glycemic block, so a new recipe whose carb ingredient lacks a GI can't ship a blank dial silently — fix by re-running the GI pipeline (below) or hand-setting the value, then rescoring. (Inflammation is computed from composition by the FII, below, not curated here.)

After any engine, food-data or ingredient change, `node scripts/rescore-recipes.mjs` regenerates every recipe's `nutrition` block (the reproducibility guard then checks each block recomputes exactly), and `node scripts/score-diff.mjs` reports what the rescore moved: per recipe, each dial's old → new value (GI and GL with band and GL basis, Nutri-Score grade, nutrient balance, inflammation score + band, processing band, kcal per serving) with its 1–10 rating move, then a count of every band transition across the archive. It compares the working tree with `HEAD` by default; `--ref <rev>` picks another revision and `--threshold <n>` lists only dial moves of at least n rating points. It only reports and always exits 0. The hand-checked synthetic recipes in `src/core/golden.test.ts` guard the verdicts themselves (an olive-oil salad stays anti-inflammatory, a jam stays a medium-GL portion) independently of the stored blocks.

## `gi-reference.json`

**Generated** GI reference table parsed from the Atkinson 2021 international tables — Supplemental Table 1, the ISO 26642:2010-compliant (higher-reliability) list — by `scripts/build-gi.mjs`. Each entry is `{ category, food, gi }` on the 100-point glucose scale; section headings are matched case-insensitively (the PDF prints "PASTA and NOODLES" in mixed case). Every numbered study row is read: because a long food name wraps onto the lines above and below its numbered row in the layout-preserved PDF, each name is reconstructed by gluing the row's own name cell to the nearest numberless name fragments in the same food category, then the GI is averaged across all study rows that resolve to the same name (an official "mean of N foods" aggregate row, where present, overrides the average). A `.xlsx` supplement in `scripts/data-raw/`, if provided, is preferred and read column-by-header instead. It is the source `scripts/match-gi.mjs` matches every carbohydrate-bearing `usda-foods.json` food against to fill `food-scoring.json` GI values.

Rebuild the GI assignments (the source PDF lives git-ignored in `scripts/data-raw/`) with:

```sh
node scripts/build-gi.mjs      # parse the tables → gi-reference.json
node scripts/match-gi.mjs --write   # assign GI + confidence into food-scoring.json (dry-run without --write;
                                    # add --rematch-predicted to re-assign the estimated tiers)
node scripts/rescore-recipes.mjs    # regenerate recipe blocks
node scripts/score-diff.mjs         # report the dial changes vs HEAD (--ref <rev>, --threshold <n>)
```

A specific reference GI is only borrowed on a strong same-category match (cross-category token matches produce nonsense, e.g. "rice vinegar" ↔ "rice"); everything weaker falls to the composition estimate or category-median/nominal tiers rather than a wrong specific value, so every food ends up with a documented GI at an honest confidence. `src/core/validate.ts` checks every recipe's stored ingredient data before it ships, with the same rules in three places: `node scripts/validate-recipes.mjs` (grouped report on stdout, errors first; `--json <path>` writes a machine-readable report; exit code 1 on any error), `src/core/validate.recipes.test.ts` (fails on errors, reports warning counts), and the /add authoring island (a live list under the ingredient table). - `DOMINANT_ENERGY` / `DOMINANT_CARB` (warning) — one ingredient carries more than 60 % of the recipe's energy or 70 % of its available carbohydrate (recipes with at least three contributing ingredients).

## Cooking factors: `retention-factors.json` + `cooking-yields.json`

Ingredients are stored raw (raw food record, raw weight) with a `cooking` method; `src/core/cooking.ts` turns each into its cooked, as-eaten state before any score is computed — the ingredient-based recipe calculation with yield and retention factors (Reinivuo & Laitinen 2007). Per ingredient, each nutrient's total is multiplied by its **retention factor** (true retention: nutrient in the cooked food ÷ nutrient in the raw food), and the mass by the **yield factor** (cooked mass ÷ raw mass); the mass change is booked as water. Energy, macronutrients, fat fractions and polyphenols carry no retention factor in either source and are kept whole. Frying adds no fat-uptake term: the cooking fat is its own ingredient and is counted in full. A matched record that is already a cooked or canned form ("Pasta, cooked", "Chickpeas, canned") is left unchanged whatever its method, so cooking is never applied twice.

Both files are **generated** by `scripts/build-retention.mjs` from the hand-curated mapping `scripts/cooking-factor-map.json` (21 cooking groups × 7 cooked methods = 147 cells) and carry provenance on every factor:

- `retention-factors.json` — `rf` per NutrientVector field with its source in `from`. Primary source: the USDA Table of Nutrient Retention Factors, Release 6 (2007), the `retn06` code named in `usda` (vitamins A, C, B1, B2, niacin, B6, folate, B12, choline; Ca, Fe, Mg, P, K, Na, Zn, Cu). Release 6 does not tabulate vitamins D, E, K, pantothenic acid, Mn or Se; those come from the Bognár 2002 Part 2 column named in `bognar` (Mn and Se from its "other minerals" row). A nutrient neither source covers is `assumed` 1.0, Bognár's own recommendation for constituents without data.
- `cooking-yields.json` — `yield` per cell with `basis` + `source`: a Bognár 2002 Part 1 weight-yield row (the mean when several rows are listed), a USDA raw/cooked record pair's water balance `(100 − water_raw) / (100 − water_cooked)` (assumes no dry-matter loss), or an explicit 1.0 `assumed` (flours, dairy, oats, boiled nuts — no tabulated yield). `overrides` hold name-specific yields within a group (broccoli 1.11 boiled, lentils 2.73, quinoa 3.42, …), matched on the food description.

Methods: `boiled` covers simmered / poached / cooked in liquid, `baked` covers oven-roasted, `fried` covers pan-fried / sautéed / stir-fried / deep-fried. A method a group has no tabulated factor for borrows its nearest neighbour (blanched → boiled, microwaved → steamed, grilled → baked, …), recorded as `usdaProxyOf` / `bognarProxyOf` / `proxyOf`. Boiled vegetables use USDA's "little water, drained" codes and grains the "water used" (absorption) codes — the middle ground between a drained side and a soup whose liquid is eaten. The food → group lookup (USDA category, then name rules: leafy / root / tomato / potato within vegetables, pasta / flour / oats within cereals, lean vs fatty fish at 5 g fat, dry pulses vs soy products) lives in `cookingGroupOf` in `src/core/cooking.ts`; fats and oils, spices, sweets, beverages, baked products and sauces have no factors and pass through unchanged.

A grain's or pulse's yield includes the water it absorbs, so the cooking water must stay an excluded ingredient (as it is by default); a grain cooked in a counted liquid (milk porridge, risotto with wine) slightly over-counts the cooked mass.

Rebuild (the USDA `retn06.txt` is downloaded into the git-ignored `scripts/data-raw/` on first run; the Bognár PDF is transcribed into the mapping by hand):

```sh
node scripts/build-retention.mjs
node scripts/rescore-recipes.mjs
```

## Food Inflammation Index data

The inflammation score is a per-food inflammatory potential computed from composition per 100 kcal (`src/core/fii.ts`), corrected by a small composition-blind food-form adjustment, energy-weighted across a recipe, nudged by a bounded aromatic adjustment (`src/core/aromatics.ts`) and banded by quantile of the food reference distribution (`src/core/inflammation.ts`). Six files back it:

- `fii-parameters.json` — the parameter table: which signals score, each one's direction (anti/pro) and weight, with a citation, plus the energy basis. Every parameter is read **per 100 kcal** (per-100 g value × 100 / max(kcal per 100 g, `minKcalPer100g` = 20)), the energy-density adjustment of the energy-adjusted dietary inflammatory index (Hébert 2019) and of the NRF9.3 balance score: water neither concentrates nor dilutes a food's profile, so dry and boiled pasta score alike and a watery herb or root is not understated next to a dry staple. The 20 kcal/100 g floor keeps near-zero-energy foods (water, salt, black coffee, tea) finite — their z-scores then stop at the ±`clampZ` caps, and salt still reads pro through its sodium. The same floor, as 0.2 kcal per gram, is the recipe aggregate's weight floor, so the energy-weighted mean of per-food tags approximates the dish's own per-kcal profile (exactly so for unclamped tags). Anti: fat quality (`(MUFA+PUFA) − (SFA+trans)`, one derived term so fat is scored once by quality), fibre, vitamins C and E, magnesium, polyphenols. Pro: free sugar, sodium. Two parameters are derived rather than read off the vector: `fatQuality_g` (above) and `freeSugar_g = max(0, sugar − 2·fibre)`, which estimates the free-sugar fraction from the 1:2 fibre:free-sugar carbohydrate-quality ratio so a whole food's intrinsic, matrix-bound sugar is not penalised like a refined sugar. Directions come from open biomarker literature, never the licensed DII effect-score constants.
- `inflammation-reference.json` — **generated** by `scripts/build-inflammation-reference.mjs`: the open reference distribution (per-nutrient robust centre/scale over the USDA corpus on the same per-100-kcal basis, the corpus centre/scale of the raw FII that each food is standardised against, and the `bands` — the quintile edges of the per-food tag distribution, so a recipe's band reflects where its score sits among single foods). Re-run the script after editing `fii-parameters.json` or `polyphenols.json`.
- `polyphenols.json` — **generated** total polyphenols (mg/100g) per `fdcId`, merged into the nutrient vector as `polyphenol_mg` (USDA carries no polyphenol column). Built by `scripts/build-phenol-explorer.mjs <export.csv> <crosswalk.json>` from the **Phenol-Explorer** "Complete composition data" export: the single Folin-Ciocalteu "Polyphenols, total" value per food (not a sum of the per-compound rows, which would double-count across the export's several analytical methods), basis `analysed:folin`. Values are analysed only, never imputed: a food is placed only when Phenol-Explorer reports the same food in the same state. The one exception is a documented absence: plain single-ingredient animal foods (meat, fish, shellfish, eggs, plain dairy) and minerals (salt, water) carry `polyphenol_mg: 0` with basis `absent:<rule>`, because polyphenols are plant secondary metabolites (Manach 2004) and Phenol-Explorer's scope is plant foods. A food with neither stays out of the file and the FII skips the parameter for it. The polyphenol referent is one-sided — centred at 0 (no measurable polyphenols = baseline) with the scale set to the median of the *analysed* contents (the rule-based zeros are excluded from the scale so they cannot shrink it) — so a low-polyphenol food never reads pro-inflammatory. Recipe-energy coverage is about 41% analysed plus 27% documented absent; the largest remaining gaps are foods Phenol-Explorer has no same-state Folin value for (whole-wheat pasta, coconut milk, tofu, honey, chickpeas). The raw export CSV is a local build input (git-ignored); the derived per-food totals and the crosswalk are committed.
- `phenol-crosswalk.json` — the hand-audited join from Phenol-Explorer food name → USDA `fdcId` that `build-phenol-explorer.mjs` reads. Each entry is verified by eye: the USDA record must be the same food in the same state (raw vs cooked/processed, whole vs peeled/dehulled, fresh vs dried). A name maps to one `fdcId` or to a list when several USDA records are that same food (e.g. avocado varieties); no `fdcId` may be placed twice, and the build fails if it is. Foods our recipes use map to the recipe's own `fdcId`. The `_absent` block lists, per rule, the `fdcId`s stored as documented-absent zeros. Phenol-Explorer foods absent from it are reported as unmatched on a run — extend it as new recipes need them.
- `food-adjustments.json` — composition-blind food-form deltas per `fdcId` (`src/core/foodAdjust.ts`): a small cited additive correction to the per-food tag for inflammatory signals composition cannot carry. Seeded with fermented dairy — yogurt and cheese read falsely pro-inflammatory from their saturated fat and sodium (and, for dairy, intrinsic lactose the free-sugar estimate over-penalises), yet are anti-inflammatory in trials. Each delta's direction is evidence-based; its magnitude is a calibration value, like the energy floor.
- `fii-aromatics.json` — the aromatic bioactive adjustment (`src/core/aromatics.ts`): ginger, turmeric, garlic, onion (incl. shallots), saffron, black pepper, thyme/oregano and rosemary act at gram doses through compounds no composition column carries, and under energy weighting a pinch weighs almost nothing. Each aromatic carries its overall inflammatory effect score from Shivappa 2014 (Table 2; used only for direction and relative size: turmeric −0.785, ginger −0.453, garlic −0.412, onion −0.301, saffron −0.140, pepper −0.131, thyme/oregano −0.102, rosemary −0.013) and, per matched `fdcId`, a typical culinary dose per serving (a dried form's dose is the fresh dose scaled by the fresh:dried energy-density ratio). Per recipe, Δ = k · Σ effect · min(1, grams per serving ÷ dose), with k = 0.5 and Δ ≥ −0.5: the credit grows with the amount used, saturates at one typical dose, and stays under one band width, so a ginger-heavy drink gains credit but its free-sugar load still dominates. The applied Δ is stored as `inflammation.aromaticAdjustment` so the block reproduces. **This term extrapolates diet-level evidence to single recipes; it is not validated per food.** Green/black tea and eugenol (also in Shivappa 2014) are left out: brewed tea's flavan-3-ols already enter through its polyphenol value at whole-drink weight, and eugenol has no reliable per-food mapping.

After changing any of these, regenerate the reference (`node scripts/build-inflammation-reference.mjs`) and rescore the recipes (`node scripts/rescore-recipes.mjs`).

### Calibration and scope

The FII is a reproducible, composition-derived estimate, not a biomarker-validated index: its parameter weights, the energy floor and the aromatic doses are principled choices, and the bands are quantiles of the food (not recipe-outcome) distribution. It is deliberately *not* calibrated against measured inflammatory biomarkers, for two reasons. First, scope: biomarker calibration regresses a *per-person, whole-diet* intake on that person's blood markers (e.g. NHANES 24-hour recalls against hs-CRP, by reduced-rank / stepwise regression, as the EDIP and Dietary Inflammation Score were built), so it needs an external paired diet-plus-biomarker cohort whose foods are keyed by NHANES's FNDDS food codes with no polyphenol values — a different artifact from this archive's per-food USDA composition vectors (keyed by `fdcId`), not a refit of the index that ships. Second, ceiling: even a fully calibrated whole-diet inflammation index explains under ~2% of the variance in inflammatory biomarkers (EPIC cohort, n ≈ 17,600; Lécuyer 2023) — about the share explained by smoking status, and far below body weight — because circulating CRP is dominated by adiposity, genetics and infection, which a food-composition index cannot see. The achievable gain from calibration is therefore bounded near zero, so the FII stays a coarse *relative* estimate by design. It is worth revisiting only if paired per-person diet-and-biomarker data is acquired for some independent reason.
